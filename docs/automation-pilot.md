# MIXIT — связанный операционный цикл

Код в ветке: существующие orders/microInfluencerDeals, основной интерфейс, общий вход и audit.js сохранены. Prod не развёрнут. Маршруты основного расширения включаются FLOW_LOGISTICS_ENABLED=1; отдельные внешние действия имеют собственные флаги.

## Товары и отправки

В текущей компьютерной форме: компактный поиск по названию/ШК/SKU/Kaspi → до шести подсказок → количество → себестоимость с точностью до тиына, проверенная сервером. По текущему ШК предлагается точное совпадение. Открытие старой формы и обновление справочника не переписывают старые расходы. Все действующие сотрудники с правом изменения могут выбирать товары; read-only сохраняется.

Выбор товаров отдельно от заявки. `/flow/` — дополнительный компьютерный/мобильный режим существующих отправок: **Сая → склад Алматы/Астана → любой назначенный сборщик → собрано/нехватка → отправка → фактическая доставка**. Одна посылка связана с несколькими видео через dealIds. Передача перевозчику не считается доставкой. Существующее подтверждение доставки с фото обновляет все связанные интеграции; прежний bulk-процесс сохранён. Старые заказы без связи не изменяются. Явная отмена доставки восстанавливает прежние товарные статусы без затирания более поздних ручных правок.

Сумма посылки не умножается на число роликов. При работе со старой строковой аналитикой не копировать одну общую себестоимость в каждое видео. Атрибуция не изменена.

Справочник готовит tools/prepare_catalog.py из Excel себестоимости и Kaspi. Только точные идентификаторы; несколько активных карточек остаются на сверке. «В продаже» не является складским остатком. Валюта KZT подтверждена пользователем. Реальные файлы и цены **не коммитить** в этот публичный репозиторий.

## CRM → интеграция

crm-link.js принимает профиль с проверенным CRM ID по FLOW_CRM_SECRET и хранит только соответствие. Из CRM открывается существующая форма интеграции, включая после входа общим аккаунтом. Создание строки не происходит до подтверждения условий менеджером. Конфликт ник/ID не сливается автоматически.

## Интеграция → Blogery Audit → утверждённая версия → блогер

blogery-client.js: кнопка «ТЗ → Blogery Audit» ставит запрос в сохраняемую очередь; BLOGERY_BRIDGE_ENABLED=1, BLOGERY_AUDIT_ORIGIN, BLOGERY_BRIDGE_SECRET включают передачу. Тот же ключ используется при повторе. После приёма доступна ссылка на запрос в **существующем Blogery Audit**.

Сервер Blogery Audit хранит связь с существующим ТЗ, утверждение, реальные DOCX/PDF и outbox. `/api/automation/brief-event` принимает результат по FLOW_INTEGRATION_SECRET. В Barter Box нет второй редактируемой базы ТЗ. Утверждённые версии неизменяемы; новое утверждение не заменяет старую отправленную версию.

Кнопка отправки ТЗ в текущей интеграции использует brief-delivery.js. Менеджер может заранее разрешить автоотправку флажком в форме; разрешение связано с проверенным телефоном и требует повторного подтверждения при его изменении. FLOW_BRIEF_SEND_MODE=on разрешает отправку PDF через существующий Wazzup. Получатель фиксируется и сверяется с текущим телефоном. Статус accepted не считается sent; sent подтверждается webhook. После него статус возвращается в Blogery Audit. Сетевой timeout — uncertain, не повторная отправка вслепую. Для WABA проверяется окно общения.

Подтверждённые videoStatus=опубликовано + publishDate + reelsLink передаются в существующие поля результата Blogery Audit вместе с доступными метриками. Один присланный URL не публикует строку.

## WhatsApp → GATE → тимлид → монтаж

FLOW_VIDEO_VERSIONS_ENABLED=1 сохраняет версии в существующем координаторе. Неоднозначное сообщение не привязывается к ближайшей дате. Выбор: POST `/api/coord/pending-media/:messageId/attach` с dealId; экран выбора находится в `/flow/` → «Входящие материалы».

Существующий GATE сохраняет исходную шкалу **9**, без умножения старых оценок. Запоздалый анализ старой версии не заменяет актуальную. PDF/счёт не считается видео только потому, что пришёл документом.

review-transport.js **реально отправляет** видео и GATE двумя связанными сообщениями по Wazzup v3. FLOW_REVIEW_SEND_MODE=dry/on; FLOW_TEAM_LEADS_JSON — проверенные телефоны тимлидов по именам Нина/Сая/Анеля. Ответ на видео или карточку связывается с version ID через quotedMessage.messageId, проверяются отправитель и канал. Согласовано → текущий vstage; правки/пересъём → соответствующий процесс; монтаж → задача. При низком GATE требуется «Согласовано: причина». Неоднозначный ответ уходит на проверку, дата не меняется.

В `/flow/` появился «Монтаж»: исходник + комментарий → самостоятельная загрузка монтажёром MP4/MOV/WebM → новая версия той же интеграции → повторный GATE → тимлид. Для защищённых видео: FLOW_MEDIA_SECRET, FLOW_PUBLIC_ORIGIN и постоянный FLOW_MEDIA_DIR. Файлы не лежат в state.json и не публикуются под /uploads. Ссылки подписываются и имеют срок. Входящие видео копируются с разрешённого домена Wazzup при настроенном хранилище; дополнительные CDN задаются FLOW_MEDIA_ALLOWED_HOSTS. Нужен постоянный диск и регламент хранения/резервирования. Временные ссылки Wazzup сами по себе не являются архивом.

## Сводки логистике

logistics-digests.js: в 12:00 и 15:00 Астана готовит одну сводку каждому нужному исполнителю; 0 задач — 0 сообщений. Сая видит распределение/нехватку/готовое, сборщик — свои сборки, логист — готовое на своём складе. FLOW_LOGISTICS_CONTACTS_JSON содержит подтверждённые контакты/роли; FLOW_LOGISTICS_DIGEST_MODE=dry/on. В тексте нет адресов и телефонов блогеров. Повтор cron не создаёт сообщение повторно.

## Оплаты

finance-client.js: одна подтверждённая сумма на выбранные видео → existing payments Blogger CRM → опрос статуса и чеков → отображение в интеграциях. FINANCE_BRIDGE_ENABLED, CRM_ORIGIN, FLOW_CRM_SECRET и FLOW_EMPLOYEE_CRM_MAP_JSON (имя Barter Box → точный ID сотрудника CRM). Никаких выплат и дублирования реестра. Без проверенной привязки блогера/сотрудника операция остановится.

Обработчик передачи проверенного счёта в Bitrix добавлен в Blogger CRM; требуется точный действующий webhook и поля «Согласования оплаты». Обычные задачи вместо него не создаются. Юридические шаблоны договора и АВР по-прежнему нужны отдельно.

## Общий webhook Wazzup

Существующий webhook не заменяется. crm-comms-relay.js передаёт события настроенного Instagram-канала в CRM_COMMS_WEBHOOK_URL с CRM_COMMS_WEBHOOK_SECRET. Приём и отправка Direct реализованы в CRM, не выдаются за доступные без Instagram-канала. Для иной структуры webhook требуется проверка payload. ## Проверки и выпуск

```sh
node --test test/automation-flow.test.js test/full-cycle.test.js
node test/http-flow.smoke.js
```

Вторая команда запускает настоящий Express server.js на временных синтетических данных без внешних ключей. Проверены auth, расчёт, общая посылка, повтор, сборка, передача, подтверждённая доставка и обратная смена статуса. Основные inline scripts проходят node --check. audit.js и attribution.js не изменены. Произвольный связный rollback всех новых бизнес-событий через старый журнал отдельно не проверялся.

До включения: backup state.json/audit/uploads/защищённых видео → тестовый сервер → сверка активных баз Blogery Audit/CRM → настройка защищённых секретов и сотрудников → тестовые контакты → браузер и физический iPhone → отдельное разрешение на боевой запуск. Код и тесты не являются подтверждением prod-работы.

## Доставка, оплаты и сроки контента

`lifecycle.js` добавляет события в существующую интеграцию, не создаёт отдельный календарь. В карточке интеграции на компьютере: «Доставка и сроки +2 / +4»; на `/flow/` в интеграциях доступны сроки и стоимость доставки. Ожидаемая доставка создаёт предварительный план; подтверждение получения блогером — материал +2 календарных дня, публикация +4. Сообщение перевозчика само по себе не запускает срок съёмки. `publishDate` не меняется. Ручной план/факт публикации защищены: новый расчёт сохраняется в `suggestedPlan` для рассмотрения менеджером.

Оплата сама по себе не запускает отсчёт. `FLOW_PAYMENT_PURPOSE_MAP_JSON` связывает фактические названия этапов CRM с `buyout`, `delivery`, `content`, например `{"выкуп":"buyout","доставка":"delivery","видео":"content"}`. При проверенном `paid` от CRM фиксируется назначение и создаётся один черновик сообщения; повторный опрос не дублирует сообщение. «Подано» не считается оплатой. Без сопоставления этапа уведомление не создаётся. Общий файловый процесс оплаты Нины не заменяется.

Сообщения пока сохраняются как черновики внутри интеграции и показываются в разделе сроков. Автоматическая отправка этих новых уведомлений в WhatsApp не подключена; включение старых транспортов само по себе их не отправляет. Входящие ответы с датами нужно подтвердить через форму; автоматическое извлечение дат из WhatsApp в эти события ещё не связано.

## Счёт подаётся из Barter Box

В основной форме интеграции «Подать на оплату»: сумма, получатель, способ расчёта, этап, связанные видео и файл счёта ИП. Менеджер подтверждает проверку счёта. Файл сохраняется в приватном `FLOW_PAYMENT_INVOICE_DIR` (по умолчанию `DATA_DIR/payment-invoices`), затем платёж регистрируется в существующем реестре Blogger CRM, файл передаётся межсерверно и существующий адаптер CRM отправляет его в процесс Bitrix «Согласование оплаты». Менеджеру не нужно повторно прикреплять файл в CRM. CRM остаётся отчётностью и единой точкой технической отправки в Bitrix, ключ Bitrix в браузер не передаётся.

Нужны FINANCE_BRIDGE_ENABLED на обоих сервисах, согласованный FLOW_CRM_SECRET, CRM_ORIGIN и сопоставление сотрудников, постоянные диски; в CRM точный вебхук, ID процесса и поля Bitrix плюс BITRIX_PAYMENT_ENABLED=1. Без реальной настройки статус не выдаётся за успешную подачу. «В CRM» и «Передано в Bitrix» показываются отдельно. Наличные не направляются в Bitrix этой веткой. Подано не означает оплачено. Повторная передача того же файла идемпотентна; другой файл для уже прикреплённого счёта отклоняется.
